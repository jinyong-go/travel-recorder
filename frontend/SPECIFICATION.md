# 여행 지도 (travel-recorder) 프론트엔드 요구사항 명세서

## 1. 개요

### 1.1 목적
사용자가 다녀온 여행 장소를 기록하고 다른 사람과 공유할 수 있는 웹 애플리케이션의 프론트엔드를 구축한다. 사용자는 네이버 계정으로 로그인한 뒤 여행 장소를 등록·저장하고, 등록된 장소를 카테고리 등으로 필터링하여 조회할 수 있다.

### 1.2 범위
본 문서는 프론트엔드(React + Vite, `frontend/`)의 기능·화면·데이터 요구사항을 정의한다. 백엔드 API 명세, 인증 서버 구현 세부사항은 본 문서의 범위 밖이며, 프론트엔드가 기대하는 연동 지점만 명시한다.

### 1.3 용어
| 용어 | 설명 |
|---|---|
| 여행지 | 사용자가 등록하는 장소 1건 (관광지/쇼핑/맛집 중 하나) |
| 등록자 | 여행지를 등록한 로그인 사용자 |
| 카테고리 | 관광지, 쇼핑, 맛집 3종 중 하나 |

## 2. 사용자 및 인증

### 2.1 로그인
- 사용자는 **네이버 로그인(NAVER OAuth 2.0)** 을 통해서만 서비스에 로그인한다. 별도의 자체 회원가입/이메일·비밀번호 로그인은 지원하지 않는다.
- 헤더 우상단에 **로그인 링크**를 배치한다. 비로그인 상태에서는 "로그인" 텍스트 링크가 노출되며, 클릭 시 로그인 화면으로 이동한다 (별도 라우트 또는 네이버 OAuth 동의 화면으로의 진입점).
- 로그인 상태에서는 헤더 우상단의 로그인 링크 자리가 사용자 프로필(이름·프로필 사진)과 로그아웃 메뉴로 대체된다.
- 비로그인 상태에서도 등록된 여행지 목록 조회·필터링·지도 보기는 가능하다 (읽기 전용, "둘러보기").
- 여행지 등록, 리뷰(별점+코멘트) 작성, 본인이 등록한 여행지 수정·삭제는 로그인한 사용자만 가능하다. 비로그인 사용자가 등록(FAB) 버튼을 클릭하면 로그인 화면으로 유도한다.
- 로그인 상태는 새로고침 후에도 유지되어야 한다 (세션/토큰 유지).
- 로그인 실패, 세션 만료 시 사용자에게 안내 메시지를 노출하고 재로그인을 유도한다.

### 2.2 권한
- 모든 로그인 사용자는 여행지를 등록할 수 있다.
- 여행지의 수정·삭제는 등록자 본인만 가능하다.
- **별점과 코멘트는 분리하지 않고 "리뷰" 한 건으로 함께 등록한다.** 별점만 남기는 것은 가능하지만, 별점 없이 코멘트만 남길 수는 없다.
- 리뷰는 여행지 1건당 로그인 사용자별로 1개만 등록 가능하며, 이후 재등록 시 기존 리뷰가 갱신된다 (별점은 평균으로 집계 표시).
- 리뷰 작성은 모든 로그인 사용자가 가능하며, 수정·삭제는 작성자 본인만 가능하다.
- 별점 값의 범위는 0.5 ~ 5.0이며 0.5점 단위로만 입력할 수 있다. 백엔드도 같은 규칙으로 저장·검증한다 (`Review.score: Double`, 0.5 단위 검증 + DB CHECK 제약).
- 평균 별점은 이 값들의 산술 평균이므로 0.5 단위가 아닐 수 있다. 백엔드는 소수점 둘째 자리까지 반올림해 내려주며, 화면에는 소수점 첫째 자리까지 표시한다(★ N.N).

## 3. 메인 페이지 (현재 구현 기준)

메인 페이지는 현재 구현되어 있는 화면 구조를 기준으로 명세한다.

### 3.1 헤더 (`app-header`)
- 좌측: 서비스 로고/타이틀. 위치 핀 아이콘 + "여행 지도" 타이틀 + "by YONG" 서브 라벨로 구성된다.
- 우측(`header-actions`): 좌측부터 순서대로 다음 요소를 배치한다.
  1. 설정 메뉴 (`SettingsMenu`) — 지도 표시 방식(새 창/페이지 내 임베드) 설정
  2. 테마 토글 — 라이트/다크 전환 (4장 참고)
  3. 로그인 링크 또는 로그인 사용자 프로필/로그아웃 메뉴 (2.1 참고)

### 3.2 카테고리 탭 (`category-tabs`)
- 전체 / 관광지 / 쇼핑 / 맛집 4개 탭을 가로로 배치한다.
- 선택된 탭은 활성(active) 스타일로 표시되고, 목록은 선택된 카테고리로 필터링된다.
- 탭 변경 시 페이지는 1페이지로 초기화된다.

### 3.3 목록 영역 (`list-section`)
- **목록 툴바**: 좌측에 총 건수("총 N건"), 우측에 정렬 선택 셀렉트(최근 등록순 / 별점순 / 거리순)를 배치한다.
- **여행지 카드 그리드** (`place-grid`): 카드 1건은 다음을 포함한다.
  - 썸네일 영역: 카테고리 아이콘(사진 미등록 시 대체) + 카테고리 배지
  - 장소명, 지역명
  - 메타 정보: 별점(★ N.N), 거리(km), 등록일
  - 메모(선택, 있을 경우만 표시)
  - "지도" 버튼 — 클릭 시 지도 모달 오픈 또는 새 창으로 네이버 지도 열기 (3.5, 5.5 참고)
- 목록이 비어 있을 경우("등록된 여행지가 없습니다.") 빈 상태 문구를 표시한다.
- **페이지네이션**: 페이지당 10건, 이전/숫자/다음 버튼으로 구성. 전체 페이지가 1페이지 이하이면 숨긴다.
- **등록 FAB**: 목록 하단(또는 화면 우하단 고정)에 "+ 등록" 플로팅 버튼을 배치한다. 클릭 시 여행지 등록 모달을 연다 (비로그인 시 로그인 유도, 2.1 참고).

### 3.4 여행지 등록 진입
- 등록 FAB 클릭 시 모달이 아닌 **별도 등록 URL 페이지**(예: `/places/register`)로 이동한다.
- 비로그인 상태에서 FAB를 클릭하면 등록 페이지로 이동하지 않고 로그인 화면으로 유도한다.
- 등록 페이지 상세 요구사항은 5.1을 따른다.

### 3.5 지도 모달
- 오버레이 클릭 또는 닫기(X) 버튼으로 닫힌다.
- 선택한 여행지의 이름/지역을 표시하고, **네이버 지도(NAVER Maps) JavaScript SDK**로 렌더링한 지도를 보여준다 (5.7 참고).
- 하단에 "새 창에서 네이버 지도로 열기" 링크를 함께 제공한다.
- 네이버 지도 Client ID가 설정되지 않은 환경에서는 모달 대신 새 창으로 네이버 지도 검색 결과를 바로 연다 (5.7 참고).

## 4. 테마 (라이트 / 다크)

- 테마는 기존의 다중 색상 선택 방식(연두/하늘/라벤더/피치/다크 5종 팔레트)에서 **라이트 / 다크 2가지 모드 토글** 방식으로 변경한다.
- 헤더의 테마 토글은 드롭다운 목록이 아닌 단일 토글(스위치 또는 아이콘 버튼, 예: 해/달 아이콘)로 라이트 ↔ 다크를 즉시 전환한다.
- 별도 선택이 없을 경우 시스템 설정(`prefers-color-scheme`)을 기본값으로 사용하고, 사용자가 토글로 명시적으로 선택하면 그 값을 우선한다.
- 선택한 테마는 로컬 저장소에 저장하여 새로고침 후에도 유지한다 (기존 `theme` 저장 방식과 동일한 패턴).
- **전체 색조는 파스텔톤 연두색을 기본 브랜드 컬러로 사용한다.**
  - 라이트 모드: 밝고 채도가 낮은 연두 파스텔을 배경 포인트/버튼/배지 등 주요 액센트 컬러로 사용하고, 배경은 화이트/아이보리 계열의 밝은 톤을 유지한다.
  - 다크 모드: 어두운 배경(짙은 그레이/그린 계열) 위에 동일한 연두 파스텔 톤을 채도·명도를 조정해 포인트 컬러로 유지하여, 두 모드 모두 "연두" 아이덴티티가 일관되게 느껴지도록 한다.
- 기존 다중 팔레트(하늘/라벤더/피치)는 더 이상 사용하지 않는다.

## 5. 기능 요구사항

### 5.1 여행지 등록 (별도 페이지)
- 등록은 모달이 아닌 **별도 등록 URL 페이지**(예: `/places/register`)에서 수행한다. 뒤로가기/취소 시 메인 목록으로 복귀한다.
- 로그인하지 않은 사용자가 등록 URL에 직접 접근한 경우 로그인 화면으로 리다이렉트한다.
- 등록 페이지는 다음 항목을 입력받는다.

| 항목 | 필수 여부 | 설명 |
|---|---|---|
| 장소명 | 필수 | **직접 입력 불가(비활성화/읽기 전용 input)**. 반드시 5.2의 장소 검색 모달에서 항목을 선택해야 채워진다 |
| 카테고리 | 필수 | 관광지 / 쇼핑 / 맛집 중 단일 선택 |
| 위치 | 필수 | 5.2 장소 검색 모달에서 장소명과 함께 자동으로 채워진다 (별도의 지도 직접 클릭 좌표 지정은 지원하지 않음) |
| 별점 | 필수 | 0.5~5.0점, **0.5점 단위** (별점 UI). 별 하나의 좌/우 절반을 각각 눌러 반 개 단위로 선택한다 |
| 사진 | 선택, 최소 1장 권장 | 이미지 파일 업로드, 다중 첨부 가능 (여러 장) |
| 코멘트/설명 | 선택 | 여행지 자체의 설명. 백엔드 `Place.memo` 로 저장되어 목록 카드에 노출된다. **상세 화면의 리뷰 코멘트(`Review.content`)와는 다른 값이다** |
| 태그 | — | 백엔드는 `Place.tags` 와 `/api/tags` 를 지원하지만 현재 등록 폼에 입력 UI 가 없다 (9장) |

- 장소명 input은 비활성화(disabled 또는 readonly) 상태로 표시되며, 그 옆에 "검색" 버튼을 배치한다. 버튼 클릭 시에만 5.2 장소 검색 모달이 열린다.
- 검색 모달에서 장소를 선택하면 폼에는 장소명 외에 위치(주소, 도로명주소, 좌표)와 **원본 링크**(5.2 참고)가 함께 채워지며, 이 값들은 화면에 노출되지 않더라도(hidden) 등록 요청 시 백엔드로 함께 전달·저장되어야 한다.
- 등록 폼은 입력값 검증(필수값 누락, 카테고리 미선택, 장소 미선택 등)을 수행하고 실패 시 인라인 오류 메시지를 표시한다. 장소를 선택하지 않은 채 제출을 시도하면 "장소를 검색해 선택해주세요" 등의 오류를 표시한다.
- 사진은 업로드 전 미리보기를 제공하며, 업로드 중 진행 상태(로딩)를 표시한다.
- **등록 버튼 한 번이 백엔드 API 3회 호출로 나뉜다** — `POST /api/places`(장소·카테고리·위치·코멘트) → `POST /api/places/{id}/photos`(사진) → `PUT /api/places/{id}/reviews`(별점). 폼의 별점은 등록자 본인의 리뷰로 저장된다. 1번이 성공하고 뒤 단계가 실패하면 사진·별점이 빠진 여행지가 남으므로, 실패한 단계를 재시도하거나 사용자에게 안내해야 한다 ([`backend/SPECIFICATION.md`](../backend/SPECIFICATION.md) §4.2b).
- 등록 성공 시 메인 목록 페이지로 이동하고, 새 항목이 반영된 것을 사용자가 확인할 수 있어야 한다 (정렬 기준이 "최근 등록순"일 때 최상단 노출).
- 등록 실패(네트워크 오류, 인증 만료 등) 시 오류를 안내하고 입력값(선택된 장소 포함)은 유지한다.

### 5.2 장소 검색 모달 (우편번호 검색 방식)
등록 페이지(`/places/register`)의 장소명 옆 "검색" 버튼(그 외 향후 장소 검색이 필요한 화면에서도 공용으로 재사용 가능)을 누르면 우편번호 검색창과 유사한 방식의 검색 모달이 열린다.

- 모달 상단에 검색어 입력창과 "검색" 버튼을 배치한다. 검색어를 입력하고 검색을 실행하면 결과 목록이 아래에 표시된다.
- 결과 목록은 **10건씩 페이지네이션** 처리한다.
- 결과는 **기준 위치(5.3 참고: 등록 시 설정된 사용자 위치, 없으면 기본 위치)로부터 가까운 거리순**으로 정렬한다.
- 결과 목록 각 항목에는 최소 장소명·주소가 표시된다. 항목 클릭 시 다음 값을 등록 폼으로 전달하고 모달을 닫는다.
  - **장소명** → 장소명 필드에 채워짐(읽기 전용 유지)
  - **위치**(주소, 도로명주소, 좌표) → 위치 필드에 채워짐
  - **원본 링크**(`link`) → 화면에는 노출하지 않는 hidden 값으로 폼 상태에 보관, 등록 제출 시 `externalLink` 로 함께 전송

> **"장소 ID" 요구는 백엔드 설계에서 기각되었다.** 아래 제약대로 네이버가 고유 식별자를 주지 않고, 자체 식별자를 만들어도 동일 장소를 안정적으로 매칭할 근거가 없어서다. 백엔드는 검색 응답에 ID 대신 `link`(원본 링크)를 내려주고, 중복 등록 여부는 좌표 근접도나 `(장소명, 주소)` 조합으로 애플리케이션에서 판단한다 ([`backend/SPECIFICATION.md`](../backend/SPECIFICATION.md) §1.5, §3.1). 따라서 프론트엔드도 `placeId` 를 보관·전송하지 않는다.
- 검색 결과가 없을 경우 빈 상태 문구를 표시한다.
- **네이버 API 연동 가능 여부 확인 결과** (구현 시 반드시 고려해야 할 제약):
  - 네이버 지역 검색(오픈 API, `openapi.naver.com/v1/search/local.json`)은 검색어 기반 POI 검색만 제공하며, 좌표/반경 기반 검색이나 거리순 정렬 파라미터를 지원하지 않는다. 또한 `display`(최대 5) 파라미터와 `start`(최대 1) 파라미터의 조합상 한 검색어당 **최대 5건**까지만 조회 가능해 자체적으로 "10건씩 페이징"을 지원하지 않는다.
  - 이 API는 브라우저에서 직접 호출할 수 없다 (CORS 미지원, Client ID/Secret 노출 문제) — **반드시 백엔드에서 프록시 호출**해야 한다.
  - 응답의 좌표(`mapx`, `mapy`)는 WGS84 경위도가 아닌 별도 좌표계(정수형, 10^7 배율)로 내려오므로 화면/지도에 사용하려면 좌표 변환이 필요하다.
  - **"장소 ID" 관련 중요 제약**: 네이버 지역 검색 오픈 API 응답에는 `title`(장소명), `category`, `address`, `roadAddress`, `mapx`, `mapy`, `link` 등만 포함되며 **고유 식별자(장소 ID) 필드를 제공하지 않는다.** 자체 식별자(해시/UUID)를 부여하는 방안도 검토했으나, 같은 장소가 검색어에 따라 조금씩 다른 이름·주소로 내려와 안정적인 매칭 근거가 되지 못해 **백엔드 설계에서 기각되었다.** 최종적으로 `Place` 는 외부 장소 ID 없이 주소·좌표·원본 링크(`externalLink`)만 저장한다.
  - 따라서 "10건씩 페이징 + 기준 위치 거리순 정렬" 요구사항을 그대로 충족하려면, 프론트엔드가 아닌 **백엔드에서** 여러 검색어 변형/추가 호출로 후보를 모으고, 좌표 변환 후 기준 위치와의 거리를 계산해 정렬·페이지네이션한 결과를 프론트엔드에 내려주는 방식으로 구현해야 한다. 이는 네이버 오픈 API 단독으로는 불가능하며 백엔드 집계 로직이 필요함을 의미한다 (9장 제약사항 참고).
  - 지도 표시/주소↔좌표 변환 자체는 네이버 지도 API v3(NCP)의 Geocoder 서브모듈로 가능하다 (5.7 참고).

### 5.3 기준 위치(현재 위치) 처리
"거리순 정렬"과 "장소 검색 결과 정렬"의 기준이 되는 사용자 위치를 다음 우선순위로 결정한다.

1. **브라우저 Geolocation API로 현재 위치 파악을 시도한다.** `navigator.geolocation.getCurrentPosition()`은 HTTPS(또는 localhost) 환경에서 기술적으로 사용 가능하며, 매 오리진마다 사용자의 명시적 권한 허용이 필요하다. 사용자가 거부하거나 브라우저/환경이 미지원인 경우 실패로 처리한다.
2. **법적 이슈 검토**: 위치정보의 보호 및 이용 등에 관한 법률(위치정보법)상, 이용자의 실시간 위치정보를 수집해 서비스에 활용·저장하는 사업은 "위치기반서비스사업자"에 해당되어 방송통신위원회 신고 의무 등이 발생할 수 있다. 이를 회피하기 위해 본 서비스는 다음 원칙을 따른다.
   - Geolocation으로 얻은 좌표는 **클라이언트에서만, 일시적으로** 사용한다 (거리순 정렬 계산, 지도 초기 중심 좌표 등).
   - 사용자의 실제 GPS 좌표를 계정·사용자 식별자와 연결해 백엔드에 저장·전송하지 않는다. (단, 사용자가 여행지 등록 폼에서 "장소"의 위치를 명시적으로 저장하는 것은 장소 정보이지 개인 위치정보가 아니므로 별개다.)
3. Geolocation을 사용할 수 없거나(미지원/거부) 사용자가 원치 않는 경우, **사용자가 직접 자신의 기준 위치를 지정**할 수 있는 UI를 제공한다 (지도 클릭 또는 5.2 장소 검색 모달로 주소 검색 후 선택). 지정한 위치는 브라우저 로컬 저장소에만 보관한다.
4. 위 1~3 어느 것도 확보되지 않은 경우 **기본 위치는 서울역**(위도 37.5546, 경도 126.9706)으로 지정한다.

### 5.4 여행지 조회 및 목록
- 3.3에서 정의한 카드 그리드/페이지네이션 구조를 따른다.
- (선택 확장) 지역/키워드 검색으로 장소명·지역을 필터링하는 검색창을 제공할 수 있다.

### 5.5 필터링
- 카테고리 탭(전체/관광지/쇼핑/맛집)으로 목록을 필터링한다.
- 정렬 옵션: 최근 등록순, 별점순, 거리순(5.3의 기준 위치 사용) 중 선택 가능.
- 카테고리 필터와 정렬은 동시에 적용 가능하며, 필터 변경 시 페이지는 1페이지로 초기화된다.

### 5.6 여행지 상세 / 리뷰·사진
- 카드 클릭 시 **별도 라우트(`/places/:placeId`)** 로 이동한다. (모달 대신 라우트를 쓰는 이유: 지도 모달과의 중첩을 피하고, 상세 URL 공유·새로고침·뒤로가기가 동작해야 하기 때문)
- 목록의 카테고리/정렬/페이지 상태는 쿼리 파라미터(`?category=&sort=&page=`)로 유지하여 상세에서 돌아와도 보존된다.
- 상세 화면에는 다음을 표시한다.
  - 장소명, 카테고리, 위치(주소), 등록자, 등록일
  - 첨부된 사진 목록 (갤러리 뷰)
  - 평균 별점 및 별점 분포
  - 리뷰 목록(작성자, 작성일, 별점, 코멘트)
  - 로그인 사용자의 경우 본인 리뷰 작성/수정 폼. **별점 입력과 코멘트 입력이 하나의 폼이며 한 번에 제출한다** (별점은 0.5점 단위, 5.1의 별점 UI와 동일 컴포넌트 사용).
  - 지도 보기 (5.7 참고)
- 리뷰는 최신순으로 표시하며, 본인이 작성한 리뷰에는 수정·삭제 버튼을 노출한다.
- 이미 리뷰를 남긴 사용자에게는 작성 폼 대신 기존 별점·코멘트가 채워진 수정 폼을 보여준다 (사용자당 1건이므로 "추가 작성"은 없다).
- 코멘트는 선택 입력이므로, 코멘트 없이 별점만 제출하는 것을 허용한다. 코멘트가 없는 리뷰는 목록에 별점과 작성자만 표시한다.

### 5.7 지도 연동 (네이버 지도)
- 여행지의 위치는 **네이버 지도(NAVER Maps) JavaScript SDK v3**로 표시한다. (기존 Google Maps Embed API에서 변경)
- 네이버 지도는 Google Maps Embed API와 달리 `<iframe src=...>` 형태의 단순 임베드 URL을 제공하지 않으므로, NCP(NAVER Cloud Platform) Client ID를 발급받아 지도 SDK 스크립트(`https://oapi.map.naver.com/openapi/v3/maps.js?ncpClientId=...`)를 로드하고 `naver.maps.Map` 인스턴스를 컨테이너에 렌더링하는 방식으로 구현한다.
- 카드 또는 상세 화면의 "지도" 버튼 클릭 시:
  - 네이버 지도 Client ID가 설정된 경우: 모달 내 지도 컨테이너에 SDK 지도를 렌더링하고 해당 좌표에 마커를 표시한다.
  - Client ID가 없는 경우: 새 창으로 네이버 지도 검색 결과(`https://map.naver.com/p/search/...`)를 연다.
- 설정 메뉴에서 사용자가 지도 표시 방식(SDK 임베드/새 창)을 선택할 수 있다.
- 주소 ↔ 좌표 변환(등록 폼에서 검색 결과의 좌표 확정 등)은 네이버 지도 API v3의 Geocoder 서브모듈(geocode/reverse geocode)을 사용한다.
- 프론트엔드 환경변수는 `VITE_NAVER_MAP_CLIENT_ID` 를 사용한다 (`VITE_GOOGLE_MAPS_API_KEY` 는 제거됨).

## 8. 비기능 요구사항
- 반응형 레이아웃: 모바일(360px~)부터 데스크톱까지 대응.
- 로딩/에러 상태: 목록 조회, 등록, 이미지 업로드, 지도 로딩 각각에 대해 로딩 인디케이터와 에러 메시지를 제공한다.
- 접근성: 모달은 `role="dialog"`/`aria-modal` 등 기존 패턴을 유지하고, 폼 입력에는 라벨을 제공한다. 테마 토글에는 현재 모드를 나타내는 `aria-label`(예: "다크 모드로 전환")을 제공한다.
- 인증 토큰 및 민감 정보는 안전하게 보관하고, 네이버 지도 Client ID 등은 환경변수(`VITE_NAVER_MAP_CLIENT_ID`)로 관리한다 (기존 `.env.example` 패턴 유지, 항목만 교체). 네이버 지역 검색 API의 Client ID/Secret은 브라우저에 노출되면 안 되므로 백엔드 전용 환경변수로만 관리한다.
- 사용자 현재 위치(Geolocation) 관련: 5.3의 원칙에 따라 실시간 GPS 좌표를 사용자 식별자와 연결해 서버에 저장·전송하지 않는다. 이는 위치정보법상 위치기반서비스사업자 신고 의무 등 법적 리스크를 최소화하기 위함이다.
- 이미지 업로드는 클라이언트에서 용량/포맷 검증 후 전송한다. 기본 제한은 **1장당 5MB, 한 번에 첨부하는 전체 합계 30MB, jpg·png·webp** 이며, 제한을 넘는 파일은 첨부 목록에 추가하지 않고 사유를 인라인 오류로 표시한다. 제한값은 환경변수(`VITE_MAX_PHOTO_SIZE_MB`, `VITE_MAX_PHOTO_TOTAL_MB`)로 조정 가능하며, 백엔드 제한(`spring.servlet.multipart.max-file-size`/`max-request-size`, `app.upload`)과 같은 값을 유지해야 한다. 클라이언트 검증은 사용자 편의용이며 최종 검증 책임은 백엔드에 있다.
- **파비콘**: 서비스 타이틀의 "by YONG(용)"과 연계하여 **용(龍) 모양**의 파비콘을 사용한다. `frontend/public/favicon.svg`를 용 형상의 SVG로 교체하며, 전체 색조(파스텔 연두)와 어울리는 라인/실루엣 스타일로 제작한다.

## 9. 제약사항 및 향후 과제
- 백엔드 API 연동 전까지는 `frontend/src/data/places.js` 의 목업 데이터로 화면을 구성하며, 실제 연동 시 API 응답 스키마에 맞춰 데이터 매핑 레이어를 추가한다.
- 네이버 로그인(OAuth), 네이버 지도(NCP Client ID), 네이버 지역 검색(오픈 API Client ID/Secret)은 각각 별도의 애플리케이션 등록·키 발급이 선행되어야 한다 (네이버 개발자센터/NCP 콘솔).
- 백엔드 보안(Spring Security)은 현재 임시 비활성화 상태이므로, 인증 연동 시 백엔드와 함께 재활성화 및 토큰 검증 방식을 확정해야 한다.
- **네이버 지역 검색 API의 구조적 한계 (기술 검증 결과, 5.2 참고)**: 검색어당 최대 5건까지만 조회 가능하고(`display` 최대 5, `start` 최대 1), 좌표/반경 파라미터나 거리순 정렬을 지원하지 않으며, 브라우저에서 직접 호출할 수 없다(CORS 미지원). "10건씩 페이징 + 거리순 정렬" 요구사항을 만족하려면 백엔드에서 후보 수집·좌표 변환·거리 계산·정렬·페이지네이션을 직접 구현해야 하며, 이 경우에도 원 검색 API 자체의 5건 상한 때문에 한 검색어로 확보 가능한 후보 풀이 제한적일 수 있다. 실제 구현 착수 전 이 제약이 서비스 요구 수준을 충족하는지 재검토가 필요하며, 필요 시 다른 POI 데이터 소스(예: 카카오 로컬 API 등) 병행 검토를 고려한다.
- **위치정보법 리스크**: 사용자 현재 위치(Geolocation)는 클라이언트 로컬 용도로만 사용하고 서버에 사용자 식별 정보와 연결해 저장하지 않는 것을 원칙으로 하되(5.3 참고), 서비스가 실제로 위치기반서비스사업자 신고 대상에 해당하는지는 법률 자문을 통해 별도로 확인이 필요하다.
- **태그 입력·필터 UI 미구현**: 백엔드는 `Place.tags` 저장과 `/api/tags` 자동완성을 지원하지만 등록 폼과 목록 필터에 태그가 없다. 연동 시 등록 요청은 빈 태그 목록으로 나간다.
- **등록이 API 3회 호출로 나뉜다**(5.1): 여행지 생성 → 사진 업로드 → 별점 등록. 중간 실패 시 부분 등록 상태가 남으므로 재시도/안내 처리가 필요하다.
- (향후 고려) 여행지 수정/삭제 UI, 여행지 공유 링크, 다중 사용자 간 여행지 즐겨찾기/스크랩 기능은 본 버전 범위 밖이며 후속 명세에서 다룬다.
